# TechStore

Интернет-магазин техники: витрина, корзина, имитация оплаты, админка и обновления в реальном времени.
Учебный проект для портфолио.

**Стек:** Next.js 16 (App Router, Cache Components) · React 19 · TypeScript · Tailwind CSS 4 · PostgreSQL + Drizzle ORM · свои сессии на JWT (jose + bcrypt) · Zod · SSE + PostgreSQL LISTEN/NOTIFY · Playwright · Docker + Caddy

## Быстрый старт

```bash
cp .env.example .env          # затем поменяй SESSION_SECRET
npm install
npm run db:local              # PostgreSQL без Docker (бинарники из node_modules)
#   или: npm run db:up        # PostgreSQL и Redis в Docker
npm run db:migrate            # создать таблицы
npm run db:seed               # 46 товаров и демо-пользователи
npm run dev                   # http://localhost:3000
```

После перезагрузки компьютера достаточно одной команды: `npm run go` — поднимет базу и сайт.

`npm run db:local stop` — остановить локальную базу. Данные лежат в `.pgdata/`.

Демо-доступ (пароль `demo12345`): `admin@techstore.ru`, `manager@techstore.ru`, `user@techstore.ru`.

## Запуск в VS Code

Открой папку проекта (`File → Open Folder…`) и нажми **Ctrl+Shift+B** — запустятся база и сайт, в терминале появится ссылка http://localhost:3000. Остальные команды — в `Terminal → Run Task…`: остановить базу (`npm run db:stop`), автотесты, проверка кода, Drizzle Studio. Для отладки с точками остановки — вкладка **Run and Debug** (Ctrl+Shift+D) → «Сайт: отладка сервера».

## Структура

```
src/
  app/
    (auth)/        вход, регистрация, server actions
    account/       кабинет покупателя
    admin/         админка (MANAGER, ADMIN)
    page.tsx       главная с каталогом
  components/      UI-примитивы и шапка
  db/
    schema.ts      11 таблиц и связи
    index.ts       пул соединений
  lib/
    auth.ts        Data Access Layer: getCurrentUser, requireRole
    session.ts     cookie-сессия

scripts/seed.ts    демо-данные
```

## Ключевые решения

- **Безопасность в два слоя.** `proxy.ts` отсекает гостей до рендера, но права ещё раз проверяет каждая страница и Server Action через `lib/auth.ts`.
- **Цены в копейках целым числом** — без ошибок округления.
- **Снимки данных в заказе** (`name_at_purchase`, `price_at_purchase`, `address_snapshot`) — смена цены не меняет старые заказы.
- **Резерв остатков** (`stock.reserved`) — два покупателя не купят последний товар одновременно.
- **Защита входа:** httpOnly-cookie, `sameSite=lax`, одинаковое время ответа для существующих и несуществующих email, проверка `?next=` от открытых редиректов.

## Фото товаров

Лежат в `public/products/<slug>/`: `1.webp` — главное фото, `2.webp`, `3.webp` — дополнительные ракурсы.
Квадрат от 1000×1000, товар целиком в кадре — карточки обрезают всё, что не квадрат.

После замены файлов запусти `npm run images:import` — скрипт обновит список фото в базе и выведет товары, у которых фото нет.
Такие товары на витрине показывают иллюстрацию категории. Фото, загруженные через админку, хранятся в `uploads/products/`.

## Почта

Письма: восстановление пароля, заказ оформлен, заказ оплачен, смена статуса.

- **Без настройки** письма уходят в тестовый ящик [Ethereal](https://ethereal.email): ссылка на просмотр — в консоли сервера и на странице «Забыли пароль?».
- **Настоящая отправка** — заполни в `.env`:

```
# Gmail: включи двухэтапную проверку → myaccount.google.com/apppasswords → создай пароль приложения
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_USER=твой@gmail.com
SMTP_PASS=пароль_приложения_16_символов
MAIL_FROM=TechStore <твой@gmail.com>
```

Для Яндекса: `SMTP_HOST=smtp.yandex.ru`, пароль приложения в id.yandex.ru → Безопасность. После правки `.env` перезапусти `npm run dev`.

## Вход через Google

Уже настроено: в Google Cloud (Google Auth Platform) создан клиент «TechStore site», ключи лежат в `.env` (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`), адрес возврата — `http://localhost:3000/api/auth/google/callback`.

Пока приложение в режиме **Testing**: войти через Google могут только тестовые пользователи (сейчас это k.abdu7744@gmail.com; добавить ещё — Google Auth Platform → Audience → Test users). Сотрудники через Google не входят — только по паролю.

Когда появится домен:

1. Google Auth Platform → **Clients → TechStore site** → в Authorized redirect URIs добавить `https://мой-домен.ru/api/auth/google/callback`.
2. **Branding**: домашняя страница, ссылки на политику конфиденциальности и условия использования, домен в Authorized domains.
3. **Audience → Publish app**. Для openid/email/profile проверка Google не нужна — после публикации войти сможет любой покупатель.
4. Те же ключи — в `.env.production` на сервере.

В разработке открывай сайт через `localhost`: Google не принимает адреса вида `192.168.x.x`.

## Поддержка

Форма на `/support` (ссылки — в шапке, футере, кабинете и у помощника). Обращение сохраняется в базе
(админка → «Обращения»), команде уходит письмо, клиенту — подтверждение от имени «Поддержка TechStore».

```
SUPPORT_INBOX=ваша@почта       # куда приходят обращения; на сайте нигде не показывается
SUPPORT_EMAIL_PUBLIC=          # адрес компании для покупателей, например support@ваш-домен.ru
```

В письме команде стоит Reply-To клиента: «Ответить» в почте сразу пишет покупателю.

**Адрес компании вместо личной почты.** Пока письма уходят через Gmail, адрес отправителя — ваш Gmail
(имя отправителя показывается как «Поддержка TechStore»). Чтобы покупатели видели только адрес компании:
1. Купите домен и включите бесплатную пересылку почты (Cloudflare Email Routing или ImprovMX):
   `support@домен → ваш Gmail`.
2. В Gmail: Настройки → Аккаунты → «Отправлять письма как» → добавьте `support@домен`.
3. В `.env`: `SUPPORT_EMAIL_PUBLIC=support@домен`, `MAIL_FROM=Поддержка TechStore <support@домен>`.

## Безопасность

- **Пароли** — argon2id (19 МБ памяти на проверку, рекомендация OWASP). У каждого хеша своя случайная соль, плюс общий «перец» `PASSWORD_PEPPER` из `.env`: его нет в базе, поэтому украденный дамп без сервера не поможет подобрать пароли. Старые bcrypt-хеши перехешируются при первом входе.
- **Подбор пароля** — после 5 неверных попыток вход в аккаунт закрыт на 15 минут (счёт по журналу в базе, работает и при переборе с разных IP). Плюс лимиты по IP на вход, регистрацию, восстановление пароля, отзывы, помощника и оформление заказа.
- **Сессии** — JWT в httpOnly-cookie (`__Host-` на сервере). Смена пароля, сброс, смена роли и кнопка «Выйти на других устройствах» сразу закрывают все остальные сессии (`users.session_version`).
- **Почта** — после регистрации приходит ссылка; без подтверждения нельзя оформить заказ. Подтверждение — по кнопке, а не при открытии ссылки (почтовые сканеры открывают ссылки сами).
- **Заголовки** — CSP, запрет встраивания в iframe, `nosniff`, HSTS, без `X-Powered-By`.
- **Секреты** — при старте в продакшене сервер проверяет `SESSION_SECRET`, `PASSWORD_PEPPER`, `CRON_SECRET` и не запустится с пустыми или примерными значениями.
- **Демо-режим** — тестовая оплата на сервере работает только при `DEMO_STORE=1`, и тогда на каждой странице видна плашка «Демо-магазин».
- **Чужие данные** — каждый запрос к заказам, адресам, отзывам, избранному и событиям заказа фильтруется по владельцу на сервере; e2e-тест проверяет, что чужой заказ по прямой ссылке не открывается. Браузер к базе не подключается, поэтому отдельная защита строк в PostgreSQL (RLS) не нужна.
- **Проверки на сервере** — цены, суммы, скидки, количество в корзине, адрес доставки, город, роль и файлы проверяются и считаются только на сервере; из браузера приходят лишь id и введённые поля, которые проходят через zod.
- **Ключи** — в коде и в истории git ключей нет: на компьютере они в `.env`, на сервере — в `.env.production` (создаёт `setup-server.sh`), в CI генерируются на один прогон.

## Сотрудники

Демо-аккаунтов с известным паролем на сервере нет: `db:seed` там не запускается. Сотрудники: `admin@techstore.ru` (админ) и `manager@techstore.ru` (менеджер).

Пароль задаётся по одноразовой ссылке — открыть в браузере и дважды ввести пароль (от 12 символов, буквы и цифры):

```bash
npm run staff -- link admin@techstore.ru        # ссылка на 30 минут, срабатывает один раз
npm run staff -- list                           # кто есть
npm run staff -- create anna@techstore.ru MANAGER "Анна"   # новый сотрудник + ссылка
npm run staff -- rename admin@techstore.ru admin@мой-домен.ru
```

На сервере то же внутри контейнера: `docker compose -f docker-compose.prod.yml exec app node scripts/staff.mjs link <email>`.

Почта сотрудника — только логин: «Забыли пароль?» им писем не шлёт, а вход через Google для них закрыт. Иначе письмо или Google-аккаунт на чужом домене открыли бы админку.

## Оплата

Тестовый шлюз устроен как настоящий: магазин создаёт платёж → покупатель платит на странице шлюза → шлюз шлёт на `/api/payments/webhook` уведомление, подписанное HMAC-SHA256. Обработка идемпотентна: повторный вебхук ничего не ломает. Товар резервируется на 15 минут; просроченные резервы снимаются автоматически и по `GET /api/cron/release` (для cron на сервере).

Тестовые карты: `4242 4242 4242 4242` — успех, `4000 0000 0000 0002` — отказ банка.

**Скидка вместо отмены.** Когда покупатель нажимает «Отменить заказ» (на странице заказа или «Передумали?» на странице оплаты), ему один раз предлагают скидку 30%. Если согласится: неоплаченный заказ получает новую сумму и новую ссылку на оплату, по оплаченному — разница возвращается на карту. Сумма считается только на сервере, повторно предложение не показывается (`users.retention_offer_at`). Процент — `RETENTION_PERCENT` в `src/lib/retention.ts`.

## Обновления в реальном времени

Без Redis и отдельного сокет-сервера: при смене статуса заказа в той же транзакции выполняется `pg_notify`, каждый процесс Next.js держит одно соединение с `LISTEN` и рассылает события по SSE (`/api/events`). Покупатель видит новый статус заказа, админ — новые заказы и выручку без перезагрузки. Если соединение оборвалось, браузер переподключается сам.

## Тесты

`npm run test:e2e` — 65+ сценариев Playwright на десктопе и телефоне: вход, восстановление пароля, корзина, город, оформление и оплата, отказ банка, подпись вебхука, живое обновление статуса, админка товаров. Тесты поднимают свой сервер на порту 3100 и **отдельную базу `techstore_test`** — рабочие данные не трогаются. Пока идут тесты, открытая вкладка `npm run go` может несколько раз перезагрузиться — это два dev-сервера в одной папке, на данные не влияет.

## Выкладка на VPS

Нужен сервер с Ubuntu 22.04/24.04 (от 2 ГБ памяти, лучше 4 ГБ) в России — персональные данные покупателей по 152-ФЗ хранятся на серверах в РФ — и домен, направленный на IP сервера (A-запись).

1. При заказе VPS добавьте в панели хостинга свой публичный SSH-ключ.
2. Настройте сервер одной командой — обновления, swap, Docker, пользователь `deploy`, вход только по ключу (root и пароли выключаются), firewall (22/80/443), fail2ban, проект и ключи в `.env.production` (генерируются на сервере):

   ```bash
   scp deploy/setup-server.sh root@IP:~ && ssh root@IP "bash setup-server.sh мой-домен.ru"
   ```

3. Впишите на сервере почту (SMTP) в `.env.production` и запустите: `docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build`.
4. Заведите админа: `docker compose -f docker-compose.prod.yml exec app node scripts/staff.mjs create admin@мой-домен.ru ADMIN` — команда выдаст ссылку для пароля.

Что поднимется: PostgreSQL, сайт (миграции применяются при старте), Caddy с автоматическим HTTPS, снятие просроченных резервов каждые 5 минут и ежедневный бэкап базы в `./backups` (хранится 14 дней). Фото из админки лежат в volume `uploads`.

Сайт ходит в базу под ролью `techstore_app`: читать и менять строки можно, удалять таблицы, менять схему и выполнять команды на сервере базы — нельзя. Миграции применяет владелец базы (`MIGRATION_DATABASE_URL`).

Автодеплой: в GitHub → Settings → Secrets and variables → Actions добавить секреты `VPS_HOST`, `VPS_USER=deploy`, `VPS_SSH_KEY` (ключ печатает `setup-server.sh`) и переменные `DEPLOY_ENABLED=true`, `DEPLOY_URL=https://мой-домен.ru`. После каждого пуша в `main`:

1. CI: проверка зависимостей на уязвимости, линтер, типы, все e2e-тесты.
2. Docker-образ собирается на серверах GitHub и кладётся в GitHub Container Registry — VPS ничего не собирает.
3. Сервер делает бэкап базы, скачивает новый образ и перезапускает сайт.
4. GitHub проверяет `/api/health` и помечает деплой красным, если сайт не поднялся.

Ещё автоматически: Dependabot раз в неделю присылает PR с обновлениями зависимостей, CodeQL проверяет код на уязвимости (вкладка Security).

Восстановить базу из бэкапа: `docker compose -f docker-compose.prod.yml exec -T postgres pg_restore -U techstore -d techstore --clean < backups/<файл>.dump`.
